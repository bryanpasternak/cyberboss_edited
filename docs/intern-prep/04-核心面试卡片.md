# Cyberboss 核心面试卡片

> 这份文档不是背诵稿。每学完一块，再回来补自己的答案。

## 卡片 1：Cyberboss 是什么

短答：

> Cyberboss 是把微信、Telegram 等日常通信渠道接入本地 Codex / Claude Code Runtime 的 Agent Bridge。它除了响应用户消息，还能通过 Reminder、随机 Check-in 和其他系统事件主动唤醒 Agent，并让 Agent 调用本地工具完成操作。

面试官真正想听：

- 解决什么问题；
- 和普通聊天机器人有什么不同；
- 最关键的技术链路是什么。

## 卡片 2：完整消息链路

短答结构：

```text
通道长轮询
→ 标准化消息
→ 身份及工作区解析
→ 线程状态检查
→ Runtime Adapter
→ Runtime Event
→ StreamDelivery
→ 原通道回复
```

必须能解释：`threadId`、`turnId` 和 Reply Target 为什么一起使用。

## 卡片 3：为什么要分 Channel 和 Runtime

短答：

> Channel 只关心怎样收发微信或 Telegram 消息；Runtime 只关心怎样启动、恢复和控制 Codex/Claude 会话。两者分开后，增加新通道时不需要重写 Agent 会话逻辑，切换模型 Runtime 时也不需要重写微信协议。

## 卡片 4：Reminder 是普通闹钟吗

短答：

> 不是。Reminder 保存的是未来要交给 Agent 的内部任务。到期后系统将它转换为 System Turn，让 Agent 结合当前上下文决定调用什么工具以及是否向用户发消息。

继续追问时要承认：

- 当前是本地 JSON 队列；
- 适合单机个人场景；
- 严格的消息确认、跨实例并发和生产级重试仍有改进空间。

## 卡片 5：如何避免消息串线

答题关键词：

- identity / sender；
- binding / workspace；
- thread / turn；
- Turn Gate；
- Pending Buffer；
- Reply Target Binding。

不要只说“代码里做了判断”，要说出状态绑定在哪个层级。

## 卡片 6：28 个工具有什么意义

短答：

> 数量不是重点。工具层把 Agent 可执行的能力收敛为有名称、说明、JSON Schema 和 Handler 的接口，再由 Service 层完成业务操作。这样可以统一参数校验、运行上下文和错误边界，而不让模型直接操作所有内部对象。

准备三个代表：

- `cyberboss_reminder_create`
- `cyberboss_timeline_write`
- `cyberboss_channel_send_file`

## 卡片 7：共读怎样防止剧透

短答：

> 前端通过心跳告诉后端当前页面；页面停留超过阈值后，对应文本区间才进入 `pushedRanges`。Agent 的回看、搜索和批注接口都会校验目标段落是否处于已读区间，因此未读内容在数据访问层就不会返回。

设计取舍：

- 比仅靠 Prompt 更可靠；
- 当前文件存储简单；
- 数据规模扩大后应考虑数据库和更严格的并发控制。

## 卡片 8：AI 写了很多代码，贡献是什么

短答：

> 我没有把贡献限定为逐字手写代码。项目中我负责提出真实场景、定义功能、选择和比较方案、拆验收标准，并通过运行、日志和源码定位推动修复与迭代。AI 提高了实现速度，但功能是否符合需求、系统怎样集成以及最终是否可用，仍需要工程判断。

下一句必须接：

> 为了对简历负责，我会对写进简历的每条链路补到能够独立画图、解释取舍并排查故障的程度。

## 卡片 9：项目最大的不足

推荐答法：

> 当前系统首先服务本地单用户场景，所以使用 JSON 文件作为轻量状态存储，部署和调试简单，但不适合直接扩展到多实例高并发。如果重新设计生产版，我会增加数据库或可靠消息队列、任务确认与幂等、统一日志和指标，并补充真实通道到 Runtime 的端到端测试。

## 卡片 10：三个项目怎样形成一条线

短答：

> 苍穹外卖证明我接触过标准业务后端；医疗 RAG 证明我做过知识检索和大模型问答；Cyberboss 进一步证明我在真实通信渠道、异步事件、会话状态和 Tool Calling 场景中做过 Agent 应用。三个项目分别承担后端基础、RAG 和 Agent 工程，不需要互相重复。
